All forecast/weather I/O stays in the *app* (`fetchWeather` in `EngineerHubScreen`); the result is passed *as data*. This spec adds William's capabilities **without crossing that line**.

Ground truth verified against:
- Theo engine: `wt-theo-racelab/RaceLab/packages/engine/src` (self-contained, **zero** `schema/src` imports)
- William engine: `wt-william-racelab/RaceLab/packages/engine/src` (imports deeply from `schema/src`)
- Schema is present and identical-roster in both worktrees; Task #16 ("adopt schema") is in flight, so William's schema imports resolve.

## 2. REPORT SHAPE BRIDGE — Theo `EngineerReport` (flat 8-part) vs William `analyzeRuns` output

These are **two different products**, not two versions of one:

| | Theo `EngineerReport` (`report.ts`) | William `EngineerReport` (`reports.ts`) |
|---|---|---|
| Subject | **one run / one bundle** → a verdict | **a SET of runs** → a session debrief |
| Shape | flat: `diagnosis, primary, secondary, do_not_touch, expected_behavior, driving_tips, confidence, rationale` | `{ run_count, track_names, span, sections: ReportSection[] }` |
| Consumed by | `ReportCard`, `RunReportCard`, `RacePlanView`, `reportstore` | **nothing in either app yet** |

### RECOMMENDATION: **(c) Keep both, namespace the type, do NOT write a William→Theo adapter.**

An adapter mapping William's 6 sections back into Theo's flat 8-part shape would be lossy and pointless — they answer different questions, and Theo's cards already have a perfectly good producer (`buildReport`). Re-porting the card renderers to William's section shape would throw away the shippable 8-part posters for no product gain.

**Concrete bridge = a rename, not a mapper:**
1. In the engine barrel, export Theo's flat report as the canonical app type and **alias William's** so they coexist:
   ```ts
   // index.ts
   export { buildReport } from "./report";
   export type { EngineerReport } from "./report";            // ← the app/card contract (unchanged)
   export { analyzeRuns } from "./reports";
   export type { EngineerReport as RunSetReport } from "./reports";   // ← William's, renamed
   export type { ReportSection, ReportLine, ReportLineKind, AnalyzeRunsOptions } from "./reports";
   ```
2. App cards keep importing `EngineerReport` → still Theo's flat shape. **Zero card changes.**
3. `analyzeRuns` becomes available as a **new** capability (multi-run debrief) under `RunSetReport`; wiring a renderer for it is out of scope for the re-port (it's a new feature, not a migration step).

**If/when a debrief screen is wanted**, the field mapping William→a *flat-ish* card is: `sections.find(id==="summary")` → header; `id==="next_plan"` line of `kind:"recommendation"` → `primary.change`+`citations`; `id==="setup_changes"` → history fold; `id==="pace"`/`"tyres"` → tiles. But that is a **new renderer**, explicitly deferred.

## 3. PLANNER FAÇADE — Theo-local `buildRacePlan` composing William's `planRaceDay`

Keep the exact signature the app already calls and the exact `RacePlan` shape `RacePlanView`/`reportstore` consume. Internally, **swap the cited-adjustment half over to William's `planRaceDay`** while keeping Theo's `applyForecast`+`buildReport` for the flat report the card renders.

New file `packages/engine/src/race-plan.ts` (Theo's old `planner.ts` body, augmented):

```ts
import type { KBData } from "./data";
import { drivingTips } from "./driving-tips";
import { buildReport, type EngineerReport } from "./report";
import { planRaceDay, type RaceDayInput, type PlannedAdjustment } from "./planner"; // William
import type { ContextBundle } from "./types";
import type { LearningTuple } from "../../schema/src/runs";
import type { WeatherObservation } from "../../schema/src/weather";
import type { TrackSnapshot } from "../../schema/src/tracks";

export interface SelectedRunSummary { /* unchanged */ }
export interface RaceWindow { /* unchanged */ }
export interface Forecast { air_temp_c?: number; humidity_pct?: number; wind_kmh?: number; rain_risk_pct?: number; }

export interface RacePlan {
  report: EngineerReport;          // Theo flat 8-part — card unchanged
  conditions_shift: string[];
  technique_tips: string[];
  readiness: string[];
  race_avg_lap_s?: number;
  adjustments?: PlannedAdjustment[];   // NEW: William's grounded, cited forecast adjustments
  refusals?: { aspect: string; message: string }[]; // NEW: grounded-or-silent gaps
}

export function buildRacePlan(
  bundle: ContextBundle,
  runs: SelectedRunSummary[],
  race: RaceWindow,
  forecast: Forecast | undefined,
  data: KBData,
  // OPTIONAL William inputs — when the app can supply schema-shaped data:
  william?: { practice: readonly LearningTuple[]; forecastObs: readonly WeatherObservation[]; track: TrackSnapshot },
): RacePlan {
  if (runs.length === 0) throw new Error("Race planning needs at least one selected run …");

  // Theo half (unchanged): forecast-shifted flat report + technique tips + readiness
  const shifted = applyForecast(bundle, forecast);            // pure, no I/O
  const sorted = [...runs].sort((a, b) => a.date.localeCompare(b.date));
  const avg = runs.map(r => r.avg_lap_s).filter((v): v is number => v !== undefined);

  // William half (NEW, optional): grounded forecast adjustments + explicit refusals
  let adjustments: PlannedAdjustment[] | undefined;
  let refusals: RacePlan["refusals"];
  if (william) {
    const res = planRaceDay(
      { practice: william.practice, forecast: william.forecastObs,
        track: william.track, chassis_template_id: bundle.chassis_template_id,
        current_setup: bundle.setup },
      data,                                   // same KBData — pure, no I/O
    );
    if (res.ok) { adjustments = res.plan.adjustments; refusals = res.plan.refusals; }
  }

  return {
    report: buildReport(shifted, data),
    conditions_shift: conditionsShift(runs, forecast),
    technique_tips: drivingTips(shifted),
    readiness: readinessFacts(sorted),
    race_avg_lap_s: avg.length ? Math.min(...avg) : undefined,
    ...(adjustments ? { adjustments } : {}),
    ...(refusals && refusals.length ? { refusals } : {}),
  };
}
// applyForecast / conditionsShift / readinessFacts / humanize: copied verbatim from Theo planner.ts
```

**Input adaptation (app data → William input shapes)** happens in `EngineerHubScreen.generatePlan` (it already holds `RunEntry[]`):
- `william.practice` = `learningTuples(selectedRuns, outcomeRecords)` (schema helper, already in Theo's schema).
- `william.forecastObs` = `[ theoForecastToObservation(forecast, startIso) ]` — a 4-line adapter mapping `{air_temp_c, rain_risk_pct, wind_kmh}` → `WeatherObservation{ observed_at: startIso, source:"auto", air_temp_c, precipitation_probability_pct: rain_risk_pct, wind_speed_kmh: wind_kmh }`. (The single value the app already fetches becomes a one-element forecast window.)
- `william.track` = `latest.track` (already a `TrackSnapshot` on `RunEntry`).

The `william` arg is **optional** so the façade compiles and renders identically before the app passes it — letting you land the façade first, wire inputs second. `RacePlanView` shows `adjustments`/`refusals` in a new fold only when present.

## 5. D18 GUARD — explicit tests/assertions

Add a single engine-level guard test `packages/engine/src/test-d18-purity.ts` (Node test, runs in CI), asserting the advice path performs **zero network/IO** and is **never entitlement-gated**:

```ts
// 1) STATIC: the advice surface must not import any IO module.
//    Scan source text of the advice-path files for forbidden imports.
const ADVICE_FILES = ["engineer.ts","report.ts","race-plan.ts","planner.ts",
                      "reports.ts","plan.ts","chat.ts","retrieval.ts",
                      "history.ts","nlu.ts","offline.ts","driving-tips.ts","data.ts"];
const FORBIDDEN = [/from ["']node:/, /require\(["']fs/, /\bfetch\(/, /XMLHttpRequest/,
                   /\bDate\.now\b/, /new Date\(\)/, /Math\.random/, /AsyncStorage/];
for (const f of ADVICE_FILES)
  for (const re of FORBIDDEN)
    assert(!re.test(read(f)), `D18 violation: ${f} matches ${re}`);

// 2) RUNTIME: stub globals to throw, then exercise every entry point.
globalThis.fetch = () => { throw new Error("D18: network on advice path"); };
// (also trap XMLHttpRequest); run with no AsyncStorage in scope.
recommend(bundle, KB);
buildReport(bundle, KB);
buildRacePlan(bundle, [run], window, forecast, KB, william);
const r = planRaceDay(raceDayInput, KB); assert(r.ok || r.reason);
const chat = new RaceEngineerChat(bundle, KB); chat.greeting(); chat.handle("it pushes mid corner");
// no throw ⇒ no fetch touched ⇒ D18 holds.

// 3) DETERMINISM: same inputs → byte-identical JSON across two calls
//    (proves no clock/RNG/order nondeterminism leaked in via William's code).
assert.deepEqual(buildReport(bundle, KB), buildReport(bundle, KB));
assert.deepEqual(planRaceDay(raceDayInput, KB), planRaceDay(raceDayInput, KB));

// 4) ADVISOR-ALWAYS-FREE: there is no entitlement parameter on any signature,
//    and no entitlement/paywall symbol may be imported on the advice path.
const ENTITLEMENT = [/entitlement/i, /isPremium/i, /paywall/i, /subscription/i, /\bpro\b.*gate/i];
for (const f of ADVICE_FILES)
  for (const re of ENTITLEMENT)
    assert(!re.test(read(f)), `Advisor must be free: ${f} references ${re}`);
```

This codifies the invariant for **all four** entry points (`recommend`, `buildReport`/`buildRacePlan`, `planRaceDay`, `RaceEngineerChat.handle`) and proves the advisor is never gated. The static-import scan catches the real risk vector: William's `reports.ts`/`planner.ts`/`history.ts` import from `schema/src` — the test pins that those schema modules (`runs`, `weather`, `tracks`, `strategy`) are themselves IO-free pure data helpers (they are: `learningTuples`/`lapStats`/`deriveSky`/`detectTyreCliff` are pure). If schema ever grows an IO import, this test fails the build.

## 6. RISKS + OPEN QUESTIONS

**Riskiest steps**
1. **`types.ts` merge** — the one file with bidirectional drift. If Theo's `evolution`/`tyres` aren't re-added after taking William's file, `report.ts`/`driving-tips.ts` stop compiling. Lowest-risk if done as an explicit additive patch, not a blind overwrite.
2. **`EngineerReport` name collision** (`report.ts` flat vs `reports.ts` sections). If the barrel doesn't alias William's to `RunSetReport`, every card's `import type { EngineerReport }` silently binds to the wrong shape → runtime card breakage with green types. Must be done in the **same commit** as vendoring `reports.ts`.
3. **Schema dependency (Task #16 gate)** — `reports.ts`/`planner.ts`/`history.ts` import `learningTuples`, `effectiveTiming`, `detectTyreCliff`, `deriveSky`, `RAIN_RISK_THRESHOLD_PCT`, `conditionsToTags`, `renderConditions` from `schema/src`. All confirmed present in Theo's worktree schema, **but Task #16 is still in-progress** — this re-port cannot merge before schema adoption lands. Hard ordering dependency.
4. **`run.result` → `run.timing`** — the reconciled schema moved summary timing under `run.timing.kind:"summary"`. `EngineerHubScreen.generatePlan`'s summary builder reads `r.result?.best_lap_s` — this will read `undefined` post-schema-adoption unless switched to `effectiveTiming(r)`. Easy to miss; silently degrades the plan.

**Needs a human / William decision**
- **A. Does Theo *want* William's `analyzeRuns` (multi-run debrief) shipped now, or deferred?** It has no renderer in either app. Recommendation: vendor the function (it's on the pure path, costs nothing) but **defer the screen**. Confirm.
- **B. Façade vs full swap for `buildRacePlan`.** The user "favored but did not finalize" the thin façade. This spec implements exactly that (Theo flat report kept; William's `planRaceDay` adds cited `adjustments`+`refusals` as *additive* fields). Confirm the additive-fields approach vs. replacing Theo's report with William's race-day plan entirely (not recommended — loses the 8-part poster).
- **C. Chat outcome hooks → outbox.** William's `OutcomeEvent` is the learning-loop *write* half. Wiring `onOutcome` into `OutcomeRecord` persistence is Task #17 (storage+outbox), not this re-port. Confirm it's out of scope here.
- **D. `historyFromTuples` wiring.** William's history re-ranking only activates if `bundle.history` (and `track.track_id`) are populated. Does `bundleFromRun` already feed `historyFromTuples(learningTuples(...))` into the bundle? If not, William's re-ranking is dormant (safe, but the headline feature does nothing until `bundle.ts` is updated — step 4.10).
- **E. KB bundle shape.** William's `data.ts` validates optional `registry`/`classes`; if Theo's `packages/kb/bundle.json` lacks them it's a no-op (fine), but if it has *malformed* ones it becomes a **build error** (`assertValidKBData` throws at app startup, `kb.ts`). Verify the bundle William and Theo ship is the same compiled artifact, or pin which KB build wins.
