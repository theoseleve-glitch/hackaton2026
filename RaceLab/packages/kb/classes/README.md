# kb/classes — racing-class data layer (B10)

- `1-8-tt-buggy.json` declares a racing class: label, class facets (`category`/`scale`/`type`), allowed `power_types`, and sheet section ids (common + per-power) that mirror `packages/schema` `COMMON_SECTIONS`/`NITRO_SECTIONS`/`BRUSHLESS_SECTIONS` exactly.
- `../chassis/registry.json` lists the chassis of the class as flat `ChassisRegistryEntry`-shaped objects (schema `cars.ts` owns the SHAPE: `chassis_id`, `template_id`, `brand`, `model`, `category`, `scale`, `type`, `default_power_type`) plus kb extras: `power_types`, `template_status`, optional `template_file`, `provenance`. Pass entries verbatim as the `registry` argument of schema `makeCar`/`classLabels`.
- **Facet vocabulary**: the canonical class-facet VALUES live in the kb data (this file + the registry) and are exported as `FACET_CATEGORIES`/`FACET_SCALES`/`FACET_TYPES` from `packages/kb/src/index.ts` — for this class `category="offroad"`, `scale="1/8"`, `type="buggy"`. The example values in schema `cars.ts` comments and its test fixture (`"buggy"`/`"offroad-competition"`) are placeholders, NOT vocabulary — `sectionApplies` matches raw strings and fails closed, so a section condition authored against any other vocabulary silently hides its section. A chassis template's own `category` field (e.g. `"1-8-nitro-buggy"` in `inferno-mp11.json`) is a different fact: the `chassis/<cat>/` extraction-directory name, never a class facet.
- **Join key**: the engine loader (`packages/engine/src/node-kb.ts`) matches registry entries to chassis templates by `template_id` (templates are globbed from `kb/chassis/*.json`). `template_file` is forward-looking metadata only, not a mechanism in code — if you ever resolve it, do so relative to `kb/chassis/` (the registry's own directory). `template_status: "full"` means the full template exists next to the registry and must resolve by `template_id`; `"pending_pdf"` means we only recorded public identity facts.
- **Consumers + validation**: `node-kb.ts` loads registry + classes into engine `KBData` (optional `registry`/`classes` fields) and `npm run bundle` ships them in `kb/bundle.json`; `packages/kb` `npm test` validates these files against the schema contract and the facet vocabulary — malformed kb data is a build error, not a warning.
- **pending_pdf pipeline**: drop the official setup-sheet + manual PDFs into `chassis/<cat>/<brand>/` → extract to a typed `<model>.md` (params, kit defaults, option catalogs, part numbers) → author the `kb/chassis/<model>.json` template (+ pdf-map) → flip the registry entry to `full` with `template_file`.
- **Grounding rule (non-negotiable)**: registry entries may record public identity facts only (brand, model, scale, class, power variants that actually exist for sale — each `provenance` says where it was verified). Never invent kit setup values, geometry numbers, or option lists for chassis without extracted PDFs — `pending_pdf` marks that honestly. No source → no entry.
